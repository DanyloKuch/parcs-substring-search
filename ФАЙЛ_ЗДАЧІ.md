## 1. Algorithm description (опис алгоритму)

**Відкрити:** `solution\substring_solution.py`, метод `solve()`, рядки **16–37**. Головний розподіл — рядки **25–33**.

**Простими словами:**
> Є великий текст з 20 мільйонів символів і слово, яке треба в ньому знайти. Один комп'ютер шукає довго. Тому ми ділимо роботу. Головний комп'ютер (master) не ділить сам текст, а ділить місця, з яких слово може початися. Ці місця рівномірно розкладаються на стільки шматків, скільки є воркерів. Кожен воркер отримує свій шматок і шукає в ньому. Потім master збирає відповіді й складає їх. Ніхто не копіює текст по мережі: воркерам передається тільки слово і межі їхнього шматка.

**По коду:**
- **Рядок 19** — `positions`: скільки є місць, з яких може початися слово.
- **Рядки 30–31** — межі шматка для воркера з номером `i`:
  ```python
  frm = positions * i // workers_used
  to = positions * (i + 1) // workers_used
  ```
  Шматки однакові й не перетинаються.
- **Рядок 32** — `self.workers[i].mymap(...)`: відправити воркеру слово і його шматок.
- **Рядок 33** — `myreduce(mapped)`: зібрати відповіді й скласти.

**Показати на екрані:** `solution\input_par.txt` — три рядки входу (довжина тексту, слово, режим `par`).

## 2. Code demonstration (демонстрація коду)

**Відкрити:** `solution\substring_solution.py`, рядки **53–89**.

**Простими словами:**
> Тепер покажу, як саме шукається слово. Спочатку текст: він не лежить у файлі, а генерується з номера кожної позиції. Це означає, що на будь-якому комп'ютері на позиції 5 буде той самий символ. Далі — сам пошук. Ми використовуємо алгоритм Кнута–Морріса–Пратта. Ідея в тому, що після невдалого порівняння не треба починати з нуля: алгоритм пам'ятає, скільки символів уже збіглося, і стрибає вперед. Для цього заздалегідь будується таблиця по самому слову. Коли знайдено повний збіг, лічильник збільшується і шукаємо далі.

**По коду:**
- **Рядки 53–59, `char_at`** — символ на позиції `index` рахується з номера позиції (хеш). Тому текст однаковий на всіх вузлах і його не треба передавати.
- **Рядки 61–71, `prefix_function`** — таблиця КМП для слова: для кожної позиції в слові вказано, на скільки можна зсунутися після помилки.
- **Рядки 74–89, `count_in_range`** — основний цикл:
  - рядок 80 — пробігаємо символи від `frm` до `to + m − 2` (додаткові `m − 1` символів потрібні, щоб слово, яке починається на межі, не обрізалося);
  - рядки 82–85 — при помилці відкочуємося за таблицею, при збігу рухаємо лічильник збігу `k`;
  - рядки 86–88 — `k == m` означає знайдене слово: збільшуємо `count` і шукаємо далі.
- **Рядок 42, `mymap`** — це функція, яку воркер виконує на своєму шматку (та сама, що в рядку 32).

**Показати на екрані:** `solution\input_seq.txt` (той самий вхід, режим `seq` — послідовний еталон на master).

## 3. Build issues description (проблеми збірки)

**Відкрити:** `solution\substring_solution.py`, **рядок 1**; `deploy\startup.sh`, **рядки 2–3**; звіт `results\Lab1_PARCS_substring_search.pdf`, розділ 6.

**Простими словами:**
> Під час налаштування були проблеми, які мене зупиняли. Головна: розв'язок виконується на старій версії Python (2.7), і вона не розуміє кирилицю в коментарях без спеціального рядка. Цей рядок — перший у файлі. Друга проблема: образ Google Cloud за замовчуванням блокує мережу між комп'ютерами. Два рядки в стартовому скрипті це виправляють. Ще я пробував спершу C# (PARCS-C#), але він працює тільки на Windows і потребує старішого .NET, якого не було під рукою. Тому перейшов на Python. Це відхилення від правила мови, яке ми мали б дотримуватися за замовчуванням, але тут C# не запускався на Linux-хмарі.

**По коду:**
- **Рядок 1, `# -*- coding: utf-8 -*-`** — без нього воркер не міг завантажити модуль з кириличними коментарями (помилка `Non-ASCII character ... no encoding declared`).
- **Рядки 2–3, `deploy\startup.sh`** — відкривають внутрішню мережу `10.0.0.0/8` і порт 8080 у фаєрволі образу. Без них воркери не реєструються (`Connection timed out`), хоча правила GCP відкриті.
- **Інше** (C#, квоти регіону, вимкнений `create-with-container`) — розказати словами, код у здачі не показувати.

## 4. Run guide (гайд запуску)

**Відкрити:** `deploy\startup.sh` (весь файл, 6 рядків) і `README.md`, розділ 4.

**Простими словами:**
> Як це запустити з нуля. Створюємо 5 віртуальних машин у Google Cloud: одну головну і чотири робочі. Всі вони однакові, різниться тільки роль, яку ми передаємо через метадані. Скрипт при старті читає роль і запускає готовий контейнер PARCS. Нічого вручну не встановлюємо. Після запуску воркери самі реєструються на головному комп'ютері. Перевіряємо це на сторінці Nodes. Щоб запустити задачу з N воркерами, вмикаємо N воркерів на цій сторінці, решту вимикаємо, і подаємо задачу через сторінку Add Job.

**По коду:**
- **Рядок 4** — читає роль вузла (`master` або `worker <IP master>`) з метаданих VM.
- **Рядок 6** — `docker run ... parcs-node` запускає готовий контейнер PARCS.
- **Команди створення** — у `README.md`, розділ 4 (фаєрвол, master, воркери).
- **Вмикання воркерів** — планувальник бере тільки увімкнених (`scheduler.py`, рядок 120, з репозиторію PARCS).

**Показати на екрані:** сторінку `http://<MASTER_IP>:8080/workers` або `results\screenshot_workers.png`. Якщо VM зупинені, сказати, що стенд вмикається командою `gcloud compute instances start` (це займає кілька хвилин), і показати скріншот.

## 5. Results table (таблиця результатів)

**Відкрити:** `results\results.csv` і звіт PDF, розділ 4. Скріншот задач: `results\screenshot_jobs.png`.

**Простими словами:**
> Ось таблиця. Перший рядок — еталон: один комп'ютер шукав слово 21 секунду. Далі — паралельні прогони з одним, двома, трьома і чотирма воркерами. Головне: у всіх рядках знайдено 19 245 збігів. Це означає, що паралельна версія дає ту саму правильну відповідь. Час падає: з 24 секунд на одному воркері до 6.5 секунди на чотирьох. Ідеально було б 4 рази швидше на чотирьох, ми отримали 3.3 раза. Різниця — це накладні витрати PARCS: передача коду і збір відповідей. Один воркер повільніший за еталон, бо накладних витрат більше, ніж виграшу. Ми зробили повторний прогін, результати майже ті самі.

**По коду:**
- **Час** — вимірюється `time.time()` у рядках 21 і 34 `substring_solution.py`.
- **Прискорення S = T₁ / T_N** — наскільки швидше, ніж еталон (наприклад, для N = 4: 21.249 / 6.466 ≈ 3.29).
- **Ефективність E = S / N** — яку частку ідеального прискорення отримали (для N = 4: 82 %).
